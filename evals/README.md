# Skill 行为评估

这里用 12 个模拟项目检查 skill 能否引导 Agent 根据证据核验变更。前 6 案保留初版评估的原始请求、ID 和证据；后 6 案覆盖指纹重复次数、规则自身变更、必需 CI 任务、用户验收追踪、消费者接入以及规则退休。

- [cases.json](cases.json)：给回答者的请求与原始资料，不含期望答案。
- [rubric.json](rubric.json)：只给评分者的语义标准，每案包含 `must` 与 `must_not`。
- [已执行的评估记录](results/README.md)：保留各轮原始回答、失败项、语义评分与内容摘要。

## 运行方式

1. 固定被评估的仓库 commit、skill 内容版本、模型及可用工具。为每案启动没有历史评估上下文的独立 Agent；向它提供 `cases.json` 的顶层 instruction、该案完整对象以及当前 `skills/test-guardrails-arbiter/` 中的 skill 与参考文件。不要提供 rubric、历史答案、历史评分或其他案例的回答。
2. 保留回答原文。回答者只分析所给模拟证据，不运行案例中的虚构命令、不访问模拟项目、不实施发布或购买。skill 中提及的检查能力不能被当作已经执行的检查。
3. 回答完成后，由独立评分者读取该案、回答和 rubric。逐条判断可观察含义，引用回答中的依据；不按固定单词或整句匹配。每案全部 `must` 满足且没有触发 `must_not` 才通过。未完成、未运行或无法确定的项单列，不计入通过。
4. 报告记录评估时间、仓库 commit 或内容标识、模型、案例 ID、回答及各评分项的证据。列出通过、失败和未完成的数量；失败时先定位 skill 缺口再修改，重跑受影响案例。不要为了得到绿色结果改写原始证据或删掉未通过案例。

如运行环境让回答者能直接读取整个仓库，应复制允许读取的 skill 文件和单个案例到隔离上下文，或使用等效的工具访问限制。仅口头要求“不看 rubric”不能证明已经避免答案泄漏。评估者与回答者可以使用同一模型，但必须使用不同且不共享评分资料的上下文。

## 判定边界

单次核验回答“当前快照有哪些有效证据，能支持什么结论”。持续门禁回答“以后每次变更是否必然触发检查，平台是否要求相应任务，下游是否正确消费失败分类”。两项分别记录；其中一项通过不能推导另一项通过。本地核验不以与任务无关的平台权限为前提。

这些案例验证 Agent 在给定资料下的处理行为。JSON 能解析、链接存在、模拟回答通过，都不等于检查器在目标代码库正常运行，也不证明真实 CI、平台保护、新会话加载或消费者接入已验收。后者需要目标环境中的实际触发、故障演练与原始回执。本仓库不提供自动调用模型 API 的评估脚本，也不在此预填未执行的结果。
