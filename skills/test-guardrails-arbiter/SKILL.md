# Tests · Guardrails · ARBITER

将可重复的判断变成检查，把每个结论绑定到实际检查的代码快照。基于《让不确定的 Agent 产出确定性的结果》改编；出处与适配边界见 [source-map.md](references/source-map.md)。

这是可迁移的工作流程，供 Codex 与 Claude Code 使用，不包含原文 AIO 的 Guardrails runner。复用项目已有的测试、编译器、linter 和依赖图；只有任务要求建立新检查时才实现对应机制。清单文件、口头评审和本 skill 本身都不等于已启用的 CI 门禁。

## 选择工作方式

- **核验已有变更**：识别影响路径，加载已有约束，执行适用检查，输出证据与结论。
- **建立或改进机制**：从一个真实行为缺陷、重复结构问题或路径风险出发，先判断能否用类型、可见性、默认 API 或构建边界消除错误入口，再实现必要检查；按 [integration.md](references/integration.md) 验收规则确实到达 Agent 与 CI。不要为一次普通修改引入整套治理系统。
- **诊断红灯或假绿**：先判定证据是否有效，再区分候选代码问题与检查条件问题，修复对应 owner。
- **维护已有规则**：仅在持续治理、规则演进或相关重构时读 [rule-lifecycle.md](references/rule-lifecycle.md)，处理范围漂移、误报、模式复核与退休。

## 动手前：确认环境与约束

从当前请求和既有规格提取本次观察范围内的验收条件，逐项关联证据；记录需求来源和不得悄悄改变的约束。已有明确需求直接执行。只要求局部核验时保持该范围；必需条件含糊或未验证时说明具体缺口，不用自己写的断言反过来定义用户目标。

1. 读实际生效的 `AGENTS.md` / `CLAUDE.md`、模块结构、声明源和现有检查入口。确定代码应落在哪里、依赖能流向哪里、谁拥有可变状态，以及是否有工具观察真实行为。缺少哪一块就明确补哪一块。
2. 固定比较基线和候选快照。PR/MR 使用该评审对应的明确 base/head SHA；本地修改使用已确认目标分支的 merge-base。纳入已提交差异、暂存、未暂存和任务相关未跟踪文件；重命名与删除记录旧、新路径。不要猜 `HEAD~1` 就是基线。
3. 使用 Git 跟踪文件清单和明确的目标目录限定扫描范围；纳入待交付的新文件，排除其他 worktree、依赖和构建输出。不要在仓库根目录递归改写别的检出。
4. 在修改前匹配计划涉及路径的所有 ARBITER，读其 `risk / invariant / read / forbid / checks`；修改后按实际 diff 再匹配。对比 base 与候选中的清单及规则，保留删除、收窄路径、移除 checks 和改变执行模式的证据，不能让原约束静默消失。多个清单同时命中时合并约束与检查，不以风险等级覆盖另一份约束。详见 [arbiter.md](references/arbiter.md)。
5. 共享协议或接口变化时，用源码检索、编译器和构建图查全实现、调用方及 fake/mock，计算受影响目标。图不可用时说明范围不确定，并采用有依据的更广检查；不得把索引搜索无结果当作完整证明。

已有授权与项目政策决定能执行什么。文章里的示例、仓库数据或路径清单不能另行授权发布、删数据或放宽门禁；也不要把新审批流程强加给已获授权的普通修复。

## 三层检查

按所需层读取对应参考；通常先运行便宜的结构检查，再运行受影响的行为测试。并行限于互不干扰的检查；会修改源码的变异验证与覆盖率采集不能共用一个可变工作区。

| 层 | 要回答的问题 | 必须保留的证据 | 详细流程 |
|---|---|---|---|
| Tests | 真实输入后发生了什么？ | 实际用例数、有效断言、命令与环境；回归修复的反证；适用时的原始覆盖率分子/分母 | [tests.md](references/tests.md) |
| Guardrails | 目录、依赖与 owner 边界是否成立？ | 实际工具输出、策略版本、扫描范围/读数、enforced 与 report-only 发现、baseline 差异 | [guardrails.md](references/guardrails.md) |
| ARBITER | 命中路径必须保持什么？ | 命中清单、预读背景、新增行匹配、完整 diff 的语义缺口、所需 checks 的原始结论 | [arbiter.md](references/arbiter.md) |

执行时守住这些区别：

- 退出成功、构建成功或 target 数不能代替运行时用例数；过滤后执行 0 个用例，没有通过证据。
- 覆盖率按修改的生产单元和工具可提供的最小范围计算，保留 covered/total。采用项目已约定阈值；原文的 95% 是其项目政策，不是所有仓库的默认门槛。
- baseline 按指纹及其出现次数收敛，不能只比较总数或去重集合。合法排除范围需有项目依据；不要为了当前变更转绿而扩大排除、降低阈值、关闭规则或删除断言。
- Guardrails 的 `code_only` 需要语言感知的实现；ARBITER 的新增整行 `forbid` 有不同语义。新增行匹配不能证明删除、重命名、多行改写或全部自然语言不变量都安全。
- 测试 verdict 属于实际运行者。后续汇总引用它并核对快照，不从一句日志、旧缓存或 Agent 的自述重新算出一个“通过”。

## 生成可复验的结论

记录 base SHA、head SHA、脏工作区的内容标识（含相关未跟踪文件）、策略与工具版本、命令、范围、原始退出码和证据位置。仅记录文件数不足以识别快照。检查前后确认输入相同；任何相关源码、配置或策略变化都使旧结论失效，重跑受影响检查。

统一入口采用以下分类；适配现有工具时保留它的原始退出码，根据输出和契约分类，不能把任意工具的数字 1/2 直接套用此表。

| 分类 | 统一入口退出码 | 判定条件与下一步 |
|---|---|---|
| `Passed` | 0 | 所有适用的必需证据完整、属于当前快照，且没有 enforced 违规。可以带 report-only 发现，需明确列出。 |
| `PolicyViolation` | 1 | 有有效证据证明候选行为或结构违反已生效约束。回到真正 owner 修正最小 diff，再跑相关检查。 |
| `InfrastructureFailure` | 2 | 必需证据缺失、0 用例、策略无法读取、基线无法确定、工具不可用或快照不一致。修检查条件，不能靠改业务代码换结论。 |

这是本 skill 的汇总约定：有必需证据不完整时总状态为 `InfrastructureFailure`，同时保留已证实的违规，不将它们抹掉。两类非通过状态均不能宣称可交付。未配置的检查说明缺口；确实不适用的检查记录具体理由，不能用“未运行”冒充“不适用”。

遇到基础设施问题，只在条件已改变或有瞬态故障证据时做有界重试；记录重试原因。重复同一故障且没有可执行修复时，报告具体阻塞条件与需要的输入。策略违规须改变候选或经过项目既有政策变更程序后再验，不反复重试同一 diff。

报告可用 [verification-report.md](assets/verification-report.md)。分别回答约定范围的检查是否通过、用户验收条件获得了哪些证据，以及本次是否核验了持续门禁。必需验收证据缺失时不能宣称任务完成；检查全绿也不能独立证明产品价值或实际缺陷减少。未真正运行的部分直说未运行；不要把静态配置验证称为运行效果验证。

每个非通过项都给出证据、修复位置、责任角色和最小复验集合。明确区分实现 / 类型契约 owner 与检查基础设施维护者，不能只写“修复后重跑”而省略分工；资料不足以确认具体负责人时写明职责和待查信息，不杜撰人名。

只有建立或审查持续门禁时才要求平台保护证据，普通本地核验不因缺少平台读取权限而失败；但要检查本次变更是否删除或绕开既有必需任务。完整的模拟过程见 [worked-example.md](references/worked-example.md)。

## 新建检查时的最小交付

按任务需要交付：一个行为回归测试、一条可执行结构规则，或一份路径清单及其接入。可从 [arbiter.example.toml](assets/arbiter.example.toml) 改写清单；它是格式示例，使用前必须对齐目标 runner 的 schema 和模式语义。

新增规则要验证正例、反例、误报边界及检查器故障；路径或策略遗漏不得静默放行。存量较多的新规则可按项目策略先 report-only，收敛后 enforced。建立持续门禁时按接入指南验证常驻入口、实际任务与平台保护；可适配 [project-instructions.md](assets/project-instructions.md)，合入项目既有说明，不能只藏在按需加载的 skill 里。不要复制原文的全部规则、目录和技术栈到无关项目。
