# Tests：证明行为，先证明测试确实执行

在修复缺陷、改变可观察行为、调整共享契约或判断一次绿灯是否可信时读本文件。

## 选择能够推翻错误实现的证据

先从用户原始需求、issue 或既有契约提取验收条件，写清输入、可观察结果和失败条件，并将每项条件关联到对应检查或明确缺口。使用 [验证报告模板](../assets/verification-report.md) 保留来源；已有明确要求直接执行，不重复确认，也不为迁就实现或测试改写目标。

优先在能覆盖该行为的最低成本层验证：纯逻辑用单元测试，边界协议用集成或契约测试，跨系统用户路径才用端到端测试。不要用断言实现文本、重复计算同一公式或只检查对象存在来替代行为断言。检查通过只证明实际覆盖的条件，不能单独证明需求完整或产品价值成立。

缺陷回归应验证测试能够区分修复前后：在隔离的临时工作区恢复缺陷或引入最小变异，确认同一测试因目标行为变红，再确认修复后变绿。不要在共享工作区覆盖别人的改动；记录变异内容与失败原因，避免把编译失败或环境启动失败误当作有效回归证据。普通文案、格式等低影响修改无需为了凑流程新增测试。

## 排除假绿

- 从测试框架的原始输出确认实际执行的用例数；构建 target 数、任务数和退出码不能替代用例数。使用 filter 时尤其要核对所选测试确实执行。
- 若本来应执行测试却运行了零个用例，或全部被跳过，证据不完整，不能报告通过。检查过滤语法、测试发现、宿主和运行条件。
- 检查新增的无条件 skip、屏蔽失败的包装器，以及无限重试到成功的辅助函数。异步等待应等就绪信号；交易等有副作用的操作应只提交一次意图，再观察完成状态。
- 结果由实际测试执行方产生。后续汇总阶段只能引用或聚合原始结果，不得把失败重新解释为通过。
- 同时保留测试进程的原始退出状态和运行时用例数。非零用例数不代表全部成功；汇总任务成功、包级 `ok`、日志中有 `passed` 都不能覆盖真实失败。

## 范围、覆盖率与环境

测试范围来自实际影响面。共享协议变化时，查找全部实现、mock、fake 和相关消费者，再利用项目真实的依赖图、构建清单或工具确认受影响范围；代码索引和模型记忆不能证明“没有其他实现”。

有覆盖率要求时，使用项目约定的标准工具和它能够报告的最小相关生产范围，保存原始 `covered / total`，再按约定计算百分比。不得混入无关代码抬高结果、增加排除项掩盖缺口，或让覆盖率替代有效断言。原文的 **95%** 是作者仓库对新增或修改生产单元的门槛；本技能不把它设为所有项目的默认值。项目未规定门槛时报告实际范围与缺口。

本地与 CI 不一致时，比较真实命令、工具版本、覆盖率插桩、并发资源、运行时版本、locale 和 fixture。根据日志缩小差异，不靠重复重跑宣称修复。原文中的模拟器争用、Bazel 和 XCTest 过滤语法是平台案例，不能直接套用到其他测试框架。

异步测试尽量用可控时钟、调度器、事件或明确的查询次数构造可复现条件；外层可保留有限超时防止任务挂死，但不能把任意墙钟等待当作行为发生的证明。

UI 和有状态集成测试还需标识身份、fixture、配置、入口路由及外部依赖，说明如何重置到目标初态、以什么信号判断就绪、观察有哪些限制。每轮按该约定重置，避免残留登录态、缓存或前一轮副作用替下一轮满足条件；不具备独立重置条件时，在报告中限定证据适用范围。

## 修改测试机制时，验证测量本身

仅在调整测试宿主、发现、过滤、分片或选择性执行机制，以及维护这套机制时增加这些检查，普通代码修改不要求每次全量运行：

- 用已知成功和已知失败的探针验证宿主确实发现并执行断言。按框架真实的预期失败及意外通过语义，或在隔离套件中核验原始失败；意外通过不能被悄悄吞掉，skip 也不能代替探针执行。
- 核对预期发现范围与实际用例身份，解释新增、移除与重命名。测试目标数量可辅助发现范围骤降，但不能替代运行时用例数。
- 依赖图驱动选择性测试时，在相同源码、配置和初态下对照一次全量与选择性结果，检查应覆盖的用例是否漏选；动态加载、反射和配置依赖尤其需要反例。后续复核时机由项目维护约定决定，不设统一周期。

受控探针的预期失败是自检证据，需与业务候选本身的测试结果分开记录。探针未捕获目标失败时，先修复测试机制，不能报告保护已经生效。

## 保存可复验结果

记录执行命令、实际用例数、失败或跳过明细、日志位置、工具环境及观察的源码快照。验证期间源码发生变化，旧结果不能证明新版本；重新执行受影响检查。工作区存在未提交改动时，仅写一个 commit SHA 不足以标识快照，还需保存相关 diff 或内容指纹。

按 [验证报告模板](../assets/verification-report.md) 汇报。缺少工具、无法发现预期测试或无法确认快照时，明确记录无法验证的原因，修复检查条件；不要把这类情况伪装成产品缺陷或通过。结合工具契约和具体日志区分断言失败与检查条件故障；不能仅因出现 `timeout` 就判基建故障，也不能把未知非零退出默认判为内容违规。尚不能归因时保留原始证据并报告判定受阻，不能据此放行。
