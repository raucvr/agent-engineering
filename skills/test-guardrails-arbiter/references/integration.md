# 接入验收：确认规则到达并被正确消费

仅在用户要求建立验证机制、接入已有工作流，或审查持续门禁是否生效时加载。本文件不要求普通代码核验改写常驻文件、创建 CI 或获取平台设置权限；本 skill 也没有自带通用执行器。

## 从项目实际入口接入

先确认 Agent 实际加载的常驻文件、路径清单、检查命令、工具契约、CI 调用点和结果消费者。沿用现有约定，不根据文件名猜测入口已生效。必须在动手前到达的规则留在实际常驻文件本体；详细操作可指向参考文件，但不能只留下一个可选 skill 的名字。

在已授权的接入工作中，使用 [项目常驻指令片段](../assets/project-instructions.md)，按项目真实路径与入口改写后合并到现有 `AGENTS.md`、`CLAUDE.md` 或等效载体，避免重复和覆盖他人约定。

片段只定义行为，需补上项目已确认的路径、资料与入口才能形成可用接入。不要照抄原书的运行器名称、退出码或工具命令；适配器的映射必须由当前工具契约和实际运行验证。

## 验证到达时机和失败消费

在隔离、可恢复的验证环境进行接入验收，记录源码和策略快照、输入及原始输出：

| 验收场景 | 需要观察到的证据 |
| --- | --- |
| 新会话处理受保护路径 | 未额外提醒具体规则前，就在首次修改前读取命中不变量；移动和删除包含旧路径 |
| 已知违规改动 | 实际执行相应检查并提供目标违规证据，消费者修复正确的 owner |
| 受控检查条件故障 | 例如隔离副本中必要策略不可读；实际结果及下游保留检查条件故障，未误改业务代码或报通过 |
| 故障恢复与正常候选 | 还原条件后，真实检查能恢复正常执行；保留故障记录，不能只留下最终绿灯 |

受控故障必须不会触发外部业务副作用；不为自检破坏共享运行环境。不能只验证报告文字中包含“三态”，还要检查本地入口、CI 包装器、报告聚合及 Agent 的实际下一步动作。正常不适用的检查可按既有政策解释范围；预期运行但被过滤、跳过或吞掉失败，不能当作已完成。

## 持续门禁需要另一组证据

核验预期 CI 任务身份、触发条件、依赖关系与实际运行记录，确认相同源码、策略和工具条件下，本地与 CI 语义一致，所需任务确实执行。比对 base / candidate 中定义任务的配置；任务被删除或更名后，剩余流水线全绿不证明原门禁还在。

若要报告“持续合并门禁已生效”，还需读取托管平台中适用于目标分支的规则，确认 required-job / required-check 身份及其保护范围；CI 文件自身可被同一候选修改，单凭“流水线必须成功”不足以证明预期任务不可消失。平台能力和策略以实际证据为准，不假定某个产品支持某种设置。

在 [验证报告](../assets/verification-report.md) 中分别记录：

- **本次候选判定**：哪些必要检查在什么快照下完成，结果是什么。
- **持续门禁接入状态**：规则到达、故障消费、预期任务及平台保护分别有哪些证据和缺口。

未做平台核验时写明“未验证”；这限制持续门禁的结论，不自动推翻有充分本地证据的一次候选判定。沿用当前用户授权处理设置；本指南不新增审批流程，也不因普通验证任务自动索取远程管理权限。
