# Guardrails：把重复的结构判断做成检查

在依赖方向、代码归属、禁止使用的 API、生成物来源或检查系统本身需要稳定判定时读本文件。

## 复用项目已有的权威入口

查明本地和 CI 实际使用的检查命令、策略文件、工具版本与扫描范围。优先复用现有编译器、linter、依赖图查询和检查入口，让同一候选改动在相同条件下得到相同结论。模型或 IDE 索引可以帮助定位，不能替代这些工具输出。

策略描述“检查什么、在哪检查、如何修复”；执行器负责解析、扫描和返回证据。两者分离能避免规则散落在脚本里，也能单独验证检查机制。无需为采用本技能迁移到 Rust、Bazel 或重建 CI；原文的六条 lane 和 `guardrails/guard` 是其仓库已有实现，本技能没有交付或假定这些命令存在。

## 一条规则应有的可判断内容

| 内容 | 需要明确的边界 |
| --- | --- |
| 稳定 ID、来源与修复提示 | 指出真实事故或反复出现的问题，指向应修改的模块或状态 owner |
| scope 与检查对象 | 精确到相关路径、target、语言或依赖边，不让局部惯例变成全仓禁令 |
| source view 与匹配语义 | 检查原始文本、代码 token、AST 还是依赖图；是否包含注释和字符串 |
| 例外 | 每条允许路径有具体原因；区分合法 owner、测试夹具和生成器文本 |
| 执行模式 | `report-only` 报告发现，`enforced` 阻止违规候选通过 |
| 扫描健康度 | 记录实际扫描范围，必要时设置经过校准的哨兵，检测扫描器失效 |

owner 指相关行为或可变状态的唯一负责模块，不能仅凭某个文件名推定写入权。修复优先发生在这个 owner；发现第二份 writer 或旁路时，恢复原来的归属关系。不要只改调用点来隐藏违规。

正则或文本检查只能证明它实际检查的事实。需要理解符号绑定、跨行语法或真实依赖的规则，优先使用适合的解析器或构建图；没有实现语义检查时，应明确缺口，不让 LLM 的认可替代确定性结果。

## 规则自身也要有证据

对照固定 base 与实际 candidate 中的规则及执行入口，列出 ID、scope / 排除项、匹配语义、必需 checks、执行模式、baseline 和 CI 任务身份的差异。规则删除、路径收窄、检查被移除、`enforced` 降为 `report-only` 或任务未执行，都不能因候选配置不再提及它而静默消失。结合旧、新路径检查覆盖关系；ARBITER 的具体匹配见 [路径清单](arbiter.md#动手后用同一范围收口)。

策略修改也属于被核验的变更。合法的迁移、误报修正或规则退休应说明原不变量如何继续成立、由什么检查接管，或按哪条既有政策调整；保留前后证据，不默认所有规则必须永远保留。旧入口在候选中已不存在时，以可复验的迁移或替代检查核验其职责，不能标成已执行。读取不到必要的基线策略或入口时，明确判定受阻。

为新检查器或实质性的规则修改准备合法与违规样例，覆盖真实边界：glob、排除项、注释或字符串、变体拼写、退出状态和证据位置。故意加入一处应被阻止的改动，确认检查会报违规，修复后恢复通过。

哨兵用于发现扫描范围意外归零或骤降，阈值来自项目正常样本。触发哨兵先核查工具、范围和策略加载；真实重构造成数量下降时，应以范围变化证据调整阈值，不能为取得绿灯直接降低下限。

建立机制或审查持续合并门禁时，再按 [接入验收](integration.md) 验证常驻入口、下游消费和托管平台的 required-job 保护。一次变更的检查通过，不等于持续门禁已经生效；普通核验无需为此申请平台设置权限。

## 存量债务与例外不混用

baseline 是历史债务台账，目标是单调收敛；其许可来源沿用项目已有政策。按 `fingerprint → count` 多重集比较，拒绝空指纹和无效计数。对每个指纹，候选台账数量不得超过固定基线数量；当前发现还必须落在允许的台账身份及数量内。指纹算法、规则语义和扫描范围变化时，先确认可比性并核验迁移映射，不能直接用重新生成的台账覆盖历史。

必须能识别两种增长：删掉旧指纹 A 后加入 B，即使总数不变仍是新债；同一指纹从 3 处复制到 4 处，即使集合不变仍是增长。清偿项应随证据从台账扣除，不留下可反复借用的额度；不得通过重写 baseline 接纳当前新增违规。维护 baseline 的执行器还应保证更新完整，不能把部分写入的台账作为下一次合法基准。

首次引入且项目已有政策允许初始化时，记录 `Bootstrap`、初始发现及快照，明确本次没有历史单调性证据；不将该项写成 `Passed`，整体按既定模式和验收条件判断。应存在历史基准却无法读取、解析失败或缺少必要 revision，属于检查条件缺失，不得用 bootstrap 放行。没有初始化政策时报告缺口，不自行建立通用豁免。

新规则先声明不变量，再做成可执行检查；有存量影响时用 `report-only` 展示并处理发现，边界和历史债务稳定后再切换为 `enforced`。监测期间仍保留已有规则的强制状态。

对确认的误报，修正精确 scope、匹配器或有依据的允许路径，并加入能区分合法与违规案例的验证。不得把“这次需要通过”当作放宽规则的理由。

需要长期维护规则时再读 [规则生命周期](rule-lifecycle.md)，记录维护者、可比扫描趋势和模式复核条件；这些治理记录不强加给每次普通修改。

若项目已有例外机制，按其授权范围记录规则、路径、原因和适用条件；临时例外保留到期或移除条件，闭环时移除例外并重跑相关检查。没有现成机制时不要自行引入通用 skip、把规则改成 `report-only` 或扩大 baseline。这里是对原文“例外应有理由”的轻量移植建议，原文未定义统一 waiver/escape 协议。

## 让失败指向正确的修复对象

| 统一含义 | 证据要求与下一步 |
| --- | --- |
| Passed | 所需检查已完成，无强制违规；仍展示 `report-only` 发现 |
| PolicyViolation | 有规则与候选改动的具体证据；回到相应 owner 修改后复验 |
| InfrastructureFailure | 策略、revision、运行器或其他必要检查条件缺失；修复检查条件后复验 |

原文运行器用 `0 / 1 / 2` 表达这三种状态。接入现有工具时核对其真实退出码与输出后再映射，不把所有非零退出都当违规，也不声称尚未实现的运行器已经返回了某个代码。保留原始状态与日志；无法归因的失败先标明判定受阻及待查原因，不靠 `timeout` 关键词或未知退出码猜测故障对象。任何必要检查无法判断时，整体不能宣称通过。

失败输出至少包含规则 ID、快照、范围、定位证据、应修改的 owner 和需要重跑的最小检查集合。策略违规不要盲目重试同一 diff；基础设施故障不要通过修改业务代码求绿灯。
