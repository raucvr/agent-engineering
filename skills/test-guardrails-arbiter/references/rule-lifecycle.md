# 规则生命周期：从实际失败生长，到结构接管后退出

仅在持续维护规则、复核 report-only 模式或重构治理机制时加载。普通候选核验只需报告当前规则及证据，不必为每次小改动建立治理台账。以下将书中的维护问题转成可迁移操作，不是已在所有项目中运行的机制。

## 为规则保留最小维护记录

复用已有规则表、issue 或维护文档，记录能支持下一次判断的内容：

| 内容 | 用途 |
| --- | --- |
| 规则 ID、来源事故或失败形态 | 解释为何存在、具体防什么 |
| 规则维护者 | 负责边界校准、误报处理、复核和退休的人或团队 |
| 行为 / 状态 owner | 发生真实违规时应修复的模块；与规则维护者不是同一职责 |
| 当前模式及复核条件 | 说明为何 report-only 或 enforced，以及何时重新判断 |
| 最近有效正反例及工具 / 策略版本 | 确认规则仍能区分合法行为与目标违规 |
| 扫描范围与发现历史 | 保留实际对象数量、指纹及次数、例外变化和对应源码快照 |

维护者可复用项目现有职责，不为采用本 skill 新建审批角色。规则没有维护安排时如实记录缺口，不能假定状态 owner 自动负责所有检查器维护。

## 比较范围，而不只看发现数量

跟踪扫描对象数量和范围清单，区分“扫描更少”与“扫描正常但违规更少”。历史比较需使用可比的源码范围、规则语义、工具版本和计数口径；路径移动要保留迁移映射，指纹变化要说明台账如何转换。

范围突降时先核查加载、过滤、glob、重命名和解析器。结构重排可能合理减少扫描对象，但须用路径与结构证据解释；违规归零也可能是检查没运行，不能自动宣布风险消失。

绝对下限和相对变化都只是信号。阈值按项目正常样本和维护目标校准，不设全局比例，不让阈值自动追随异常低值。已证实的范围变化才更新比较基准，并保留调整前后的证据。

## 复核模式与误报

对长期 report-only 的规则给出下一步：继续采样并说明缺什么数据、校准边界、按既有政策启用 enforced，或删除已无明确用途的规则。复核条件可以来自重构、误报增长、样本足够或现有维护周期，不强制统一天数、规则数量或违规阈值。

区分合法修正与为了求绿绕过：记录触发失败的真实案例、误报原因、修改前后范围以及修正后的正反例。误报反复出现或例外扩散时，重新选择匹配语义或改用类型、可见性与依赖结构；不要靠不断增加 skip 维持表面通过。baseline 仍按 [多重集单调性](guardrails.md#存量债务与例外不混用) 管理。

## 结构接管后退休

规则不必永久累积。若类型可见性、唯一构造入口、依赖图或其他真实机制已承担原不变量，先证明它覆盖原先合法与违规边界，且实际生效。例如原违规写法如今被编译器稳定拒绝；自然语言上“更合理”不能代替接管证据。

按项目已有变更流程删除重复规则及失效引用，保留退休原因、接管位置、工具证据和适用边界；若只接管部分范围，保留其余有效检查。同步更新路径清单、维护记录和需要调整的调用入口，避免必需 checks 悬空。涉及持续门禁时按 [接入验收](integration.md) 核对实际任务和保护状态。

“不再报告违规”“已经没人抱怨”和“文件仍存在”都不足以证明可退休或仍在生效。结论来自覆盖关系与实际运行，不能由规则数量或绿灯数量代替。
